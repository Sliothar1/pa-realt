# Addendum: pa-core data migration (representation change only)

Written 11 Oct 2026 (Europe/Dublin) on branch `pa-core`, cut from `main` at `be232ca`, **before any
comparison was run**. (The file name follows the migration plan, which scheduled this for 12 Oct.)
It is a dated addendum to `prereg/tests_v1.json` and `prereg/addendum_v1.md`; it changes nothing in them.

**Output representation changed; scientific pipeline unchanged.** The SMR monument table now passes
through the shared PA data contract (pa-core v0.2.0, vendored at `vendor/pa-core`):
`build_data.py` → `data/monuments.csv` + `data/monuments_meta.json` → pa-core `tabular` adapter →
`data/d4m/A_mon.tsv` + `A_prov.tsv` → `pa-d4m validate` → `pa-d4m export` (default-deny allowlist)
→ `scripts/site_data.py` → `site/data/sites.json` + `site/data/standing.json`. Rows are renamed
`SMR123` → `mon:SMR123` inside `data/d4m/` only; published ids are unchanged.

`scripts/horizon_all.py`, `scripts/horizon.py`, `scripts/astro.py`, `data/tests/*`. The branch

## Parity definition
1. **Published outputs.** After running the new pipeline, every file under `site/` is compared with
   `main`. `site/data/sites.json` and `site/data/standing.json` must be byte-identical; if they are
   not, they pass only if canonical-JSON equal
   (`json.dumps(json.load(f), ensure_ascii=False, sort_keys=True, separators=(",", ":"))`: same
   values, types, list order), and the result must say which level passed. Every other `site/` file
   must be byte-identical (the migration does not write them).
2. **Prereg tests_v1.** The frozen scorer `scripts/run_tests.py` is re-run on the branch's
   `site/data/sites.json` and must reproduce the committed `site/data/tests_v1.json` and
   `data/tests/results_v1.json` byte for byte. `run_tests.py` also needs
   `data/tests/horizons_all.npz`, which is not committed, so it is regenerated with the frozen
   `scripts/horizon_all.py` from the Copernicus GLO-30 tiles (`fetch_data.sh`), on `main` and on
   the branch, in the same environment.
   - Baseline first: the `main` re-run must itself reproduce the committed files. If it does not
     (environment drift such as a different numpy), that is reported, and the criterion becomes:
     branch re-run byte-identical to the `main` re-run in the same environment, **and** every
     verdict, n, statistic and p value equal to `TEST_LOG.md`. Any branch-vs-main difference fails.
3. **D4M side files** (`data/d4m/A_prop.tsv`, `A_sky.tsv`, not published) change on purpose:
   rows get the `mon:` prefix, sky azimuths are typed floats. Check: every old triple `(r, c, v)`
   maps one-to-one to `(mon:r, c, v)` with `float(v_old) == v_new` for `A_sky`, and no triple is
   added or lost.
4. **Diff guard.** `pa-d4m diff --strict` of the branch dataset against itself rebuilt from scratch
   shows no change, and no row type drops.

Merge to `main` only if 1–4 all hold. If any fails: stop, do not merge, report the diff.
